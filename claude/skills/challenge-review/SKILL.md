# Challenge Review

Reviews one candidate's submission repo against its challenge spec + internal rubric, producing three deliverables. Phases build on each other — the interview script quotes evidence found during evaluation — so run them in order, but only run the phases the user asked for (e.g. "just the interview script" reuses an existing evaluation report if one is present).

## Inputs

- **Candidate repo**: the working directory (or a path the user names).
- **Challenge spec + internal rubric**: usually in a sibling `instructions/` directory. If none match the submission, ask the user for the criteria — don't invent a rubric.

## Phases

| Phase | Read first | Output | Location |
|---|---|---|---|
| 1. Evaluate | [EVALUATION.md](EVALUATION.md) | `evaluation-<challenge>-<candidate>.md` | **Outside** the candidate repo (parent dir) |
| 2. Verification guide | [VERIFICATION.md](VERIFICATION.md) | `manual-verification-guide-<challenge>-<candidate>.md` | Outside the candidate repo |
| 3. Interview script | [INTERVIEW.md](INTERVIEW.md) | `INTERVIEW-SCRIPT-{FIRST-TWO}.docx` + `.html` | Candidate repo root (untracked) |

## Non-negotiables

- **Run, don't trust.** The evaluation's claims come from executed commands (compose up, curl probes, parallel-request concurrency checks, the candidate's own test suite) and read code — never from the README alone. The README-vs-code cross-check is itself a rubric criterion (strongest AI tell).
- **Internal documents.** Everything produced is hiring-internal: mark reports `INTERNAL`, keep phase 1–2 outputs out of the candidate's git repo, and remind the user not to commit or share the interview files placed in the repo.
- **Verbal-only interviews by default.** No live coding unless the user asks; rubric change-requests become talk-through design questions.
- **Scoresheet from the template.** The interactive HTML is generated by `scripts/build_scoresheet.py` from a JSON data file + `assets/scoresheet-template.html` — never hand-written.
- **Leave the stack running** after verification (the user typically wants to poke around); tell them, and give the teardown command.

## Quick start (full pipeline)

1. Read spec + rubric fully → static review → boot stack → curl the rules (incl. true parallel concurrency) → run their tests → score → write report. (EVALUATION.md)
2. Turn everything you verified into a reproducible two-part guide with expected outputs + final checklist. (VERIFICATION.md)
3. Design questions from the evidence (authorship probes marked), emit docx via pandoc and HTML via the build script, verify the HTML renders and scores. (INTERVIEW.md)
